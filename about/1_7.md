# TASK-1.7: Глобальная обработка ошибок (Exception Filters)

## Контекст и цель задачи

В процессе работы микросервиса неизбежно будут возникать ошибки: от стандартных HTTP-ошибок (404 Not Found, 400 Bad Request) до специфичных ошибок базы данных (например, когда пользователь пытается проголосовать дважды и нарушает уникальный индекс `@@unique` в таблице `votes`).

По умолчанию NestJS и Prisma отдают сырые и иногда небезопасные (содержащие детали БД) ответы. Наша цель — создать глобальный фильтр исключений (Global Exception Filter), который перехватывает все ошибки и приводит их к единому безопасному JSON-формату, удобному для парсинга на стороне API Gateway.

_Напоминание: согласно стандартам, примеры кода реализации скрыты. Разработчик должен самостоятельно написать класс фильтра, используя документацию NestJS._

## Что нужно сделать разработчику (Action Items)

### 1\. Создание класса глобального фильтра

-   В папке `src/common/filters/` создать класс (например, `GlobalExceptionFilter`), реализующий интерфейс `ExceptionFilter`.
-   Декорировать класс с помощью `@Catch()`, чтобы он перехватывал абсолютно все необработанные исключения (`Error`, `HttpException`, исключения Prisma).

### 2\. Реализация логики маппинга ошибок

Внутри метода `catch` необходимо проверять тип пришедшего исключения и формировать соответствующий HTTP-ответ:

-   **Для `HttpException` (стандартные ошибки NestJS):**
    
    -   Извлекать статус-код (например, 400, 404).
    -   Извлекать сообщение об ошибке (особенно важно для ошибок валидации DTO).
-   **Для `PrismaClientKnownRequestError` (Ошибки БД):**
    
    -   Перехватывать код `P2002` (Unique constraint failed). Если нарушена уникальность (например, дубль голоса), возвращать статус `409 Conflict` (или `400 Bad Request`) с кодом `DUPLICATE_ENTRY`.
    -   Перехватывать код `P2025` (Record to update not found). Возвращать `404 Not Found` с кодом `RECORD_NOT_FOUND`.
-   **Для неизвестных ошибок (`Error`):**
    
    -   Возвращать статус `500 Internal Server Error` с безопасным кодом `INTERNAL_ERROR`. Текст оригинальной ошибки логировать в консоль (через Logger из TASK-0.4), но **никогда не отдавать клиенту**.

### 3\. Единая структура ответа (API Model)

Независимо от типа ошибки, фильтр должен формировать JSON-ответ по следующей структуре (совместимо с API Spec):

```
{
  "error": {
    "code": "STRING_ERROR_CODE",
    "message": "Человекочитаемое описание ошибки или массив ошибок валидации",
    "details": {},
    "timestamp": "2023-10-27T10:00:00Z",
    "path": "/api/v1/suggestions/sug_123"
  }
}
```
-   Поле `path` должно содержать путь запроса без хоста. Использовать **`request.url`** (включая query-параметры при необходимости) или эквивалент из контекста запроса.
-   Поле `details` — опциональный объект с дополнительными данными (например, `categoryId`, `suggestionCount` для ошибки CATEGORY_IN_USE).

### 4\. Глобальная регистрация фильтра

-   Подключить созданный фильтр глобально. Это можно сделать либо в `main.ts` через `app.useGlobalFilters()`, либо в `app.module.ts` через провайдер с токеном `APP_FILTER`.

## Критерии выполнения (Definition of Done)

-   \[ \] В проекте создан и подключен класс глобального фильтра исключений.
-   \[ \] При вызове несуществующего роута (404) микросервис возвращает ответ в едином утвержденном формате (объект `error` с полями `code`, `message`, `details`, `timestamp`, `path`).
-   \[ \] При попытке создать запись в БД, нарушающую уникальный индекс (например, дубль `[companyId, userId]` в `BannedUser`), микросервис не падает с 500 ошибкой Prisma, а корректно перехватывает `P2002` и возвращает структурированный `409 Conflict` или `400 Bad Request`.
-   \[ \] Внутренние ошибки (500) логируются, но наружу отдается только безопасное сообщение (без стектрейса и деталей SQL-запросов).
