# TASK-6.3: Сценарий B - Модерация и Team Chat (Admin Flow)

## Контекст и цель задачи

Второй Smoke-сценарий предназначен для проверки административной логики. Модераторы имеют доступ к изменению статусов, ведению закрытых обсуждений и управлению черным списком. Нам нужно убедиться, что эти действия корректно обновляют состояние базы данных, а бан (Blacklist) действительно блокирует пользователя.

Этот тест проверит работу State Machine (смена статусов), CommentsService (публичные и приватные комментарии) и BansService (система модерации).

## Что нужно сделать разработчику (Action Items)

### 1\. Подготовка тестового блока

Добавить блок `describe('Scenario B: Admin Flow', () => { ... })`. Для чистоты эксперимента можно использовать `id` предложения, созданного в Сценарии A (если тесты идут последовательно), либо создать новое в хуке `beforeAll` этого блока.

### 2\. Шаг 1: Смена статуса предложения

-   **Действие:** Выполнить `PATCH /api/v1/suggestions/:id/status` от лица администратора (`X-User-Id: admin_999`).
-   **Payload:** `{ "status": "OPEN" }`.
-   **Проверки (Expectations):**
    
    -   Статус `200 OK`.
    -   В ответе возвращается обновленный объект с `status: 'OPEN'`.
    -   _Примечание: В E2E тесте мы не проверяем отправку сообщения в Discord, так как Discord API мокается или отключается на уровне тестового модуля, но сама смена статуса в БД должна пройти._

### 3\. Шаг 2: Внутренний комментарий (Team Chat)

-   **Действие:** Выполнить `POST /api/v1/suggestions/:id/comments` с заголовком `X-User-Id: admin_999` (authorId берётся из заголовка, см. TASK-3.4).
-   **Payload:** `{ "body": "Проверил, берем в работу", "isInternal": true }`.
-   **Проверки:**
    
    -   Статус `201 Created`.
    -   При запросе `GET /api/v1/suggestions/:id/comments` этот комментарий должен присутствовать в списке с флагом `isInternal: true`.

### 4\. Шаг 3: Публичный комментарий

-   **Действие:** Выполнить `POST /api/v1/suggestions/:id/comments` с заголовком `X-User-Id: admin_999`.
-   **Payload:** `{ "body": "Спасибо за идею, скоро реализуем!", "isInternal": false }`.
-   **Проверки:**
    
    -   Статус `201 Created`.
    -   Запрос списка комментариев возвращает оба комментария.

### 5\. Шаг 4: Бан нарушителя

-   **Действие:** Эмулируем блокировку пользователя B. Выполнить `POST /api/v1/bans`.
-   **Payload:** `{ "userId": "user_B_456" }`.
-   **Проверки:**
    
    -   Статус `201 Created` (или `200 OK`).
    -   Выполнение `GET /api/v1/bans` должно возвращать массив, содержащий `user_B_456`.

### 6\. Шаг 5: Проверка действия бана

Самый важный шаг — убедиться, что бан работает на уровне бизнес-логики.

-   **Действие:** Попытаться выполнить `POST /api/v1/suggestions/:id/vote` (оставить голос) от лица заблокированного пользователя (`X-User-Id: user_B_456`).
-   **Проверки:**
    
    -   Статус ответа **НЕ** должен быть 200/201.
    -   Ожидается статус `403 Forbidden` (или `400 Bad Request`) с кодом ошибки, указывающим на бан (например, `USER_BANNED`).

### 7\. Шаг 6: Разбан (Очистка)

-   **Действие:** Выполнить `DELETE /api/v1/bans/user_B_456`.
-   **Проверки:**
    
    -   Статус `200 OK`.
    -   Повторная попытка голосования от пользователя B теперь должна проходить успешно.

## Критерии выполнения (Definition of Done)

-   \[ \] Сценарий Admin Flow успешно проходит все шаги.
-   \[ \] Подтверждена работоспособность API смены статусов и комментариев.
-   \[ \] Доказано, что `BansService` надежно блокирует мутирующие действия (голосование/создание предложений) для пользователей из черного списка.
