# TASK-6.2: Сценарий A - Жизненный цикл идеи (User Flow)

## Контекст и цель задачи

Первый и самый важный E2E-сценарий (Smoke Test) должен проверить базовый "счастливый путь" (Happy Path) обычного пользователя. Мы будем эмулировать ситуацию, когда один пользователь (User A) предлагает идею и прикрепляет картинки, а другой (User B) заходит на сайт, видит эту идею, голосует за нее, а затем меняет свое мнение.

Этот тест проверит работу сразу нескольких изолированных доменов: CRUD предложений, механику транзакционного голосования (Toggle Engine) и чтение статуса голоса (`userVote`).

## Что нужно сделать разработчику (Action Items)

### 1\. Подготовка тестового блока

В файле `test/suggestions.e2e-spec.ts` (созданном в TASK-6.1) добавить блок `describe('Scenario A: User Flow', () => { ... })`. Все HTTP-запросы внутри этого блока должны выполняться последовательно (используя `await`), так как они зависят друг от друга.

### 2\. Шаг 1: Создание предложения (User A)

-   **Действие:** Выполнить `POST /api/v1/suggestions` от лица User A (`X-User-Id: user_A_123`).
-   **Payload:** Передать `title`, `description`, `category` и массив `images` (с парой моковых URL-ов).
-   **Проверки (Expectations):**
    
    -   Статус ответа `201 Created`.
    -   В теле ответа присутствует сгенерированный `id` (сохранить его в переменную `createdSuggestionId` для следующих шагов).
    -   Поле `status` равно `NEW`.

### 3\. Шаг 2: Чтение списка (User B)

-   **Действие:** Выполнить `GET /api/v1/suggestions` от лица User B (`X-User-Id: user_B_456`).
-   **Проверки:**
    
    -   Статус `200 OK`.
    -   Массив `items` содержит хотя бы один элемент.
    -   Найти в массиве элемент с `id === createdSuggestionId`.
    -   Проверить, что его `userVote` строго равен `null` (User B еще не голосовал).

### 4\. Шаг 3: Первое голосование и проверка (User B)

-   **Действие:** Выполнить `POST /api/v1/suggestions/:id/vote` (используя сохраненный ID). Заголовок: User B. Тело: **`{ "vote": "upvote" }`**.
-   **Проверки:**
    
    -   Статус `200` или `201`.
    -   Ответ содержит `{ upvotes: 1, downvotes: 0 }`.
-   **Дополнительная проверка (User Vote State):**
    
    -   Выполнить `GET /api/v1/suggestions/:id` от лица User B.
    -   Убедиться, что в деталях предложения поле `userVote` равно `1`.

### 5\. Шаг 4: Голосование второго пользователя (User A)

-   **Действие:** Выполнить тот же `POST /vote` от лица автора (User A). Тело: **`{ "vote": "upvote" }`**.
-   **Проверки:**
    
    -   Ответ содержит обновленные счетчики: `{ upvotes: 2, downvotes: 0 }`.

### 6\. Шаг 5: Переключение голоса / Toggle (User B)

-   **Действие:** Выполнить `POST /vote` от лица User B. Тело: **`{ "vote": "downvote" }`**. Юзер передумал.
-   **Проверки:**
    
    -   Сервер не должен падать с 500 ошибкой уникальности. Он должен корректно обновить голос.
    -   Ответ должен содержать `{ upvotes: 1, downvotes: 1 }` (один голос "за" от User A, один "против" от User B).

### 7\. Шаг 6: Проверка Lazy Sync профиля

Благодаря механизму **Lazy Create** (TASK-2.1), пользователи A и B автоматически создаются в БД при первых действиях в сценарии (создание идеи, голос). Предварительное сидирование пользователей в E2E не требуется. Эндпоинт **`GET /api/v1/users/me`** описан в TASK-3.7.

-   **Действие:** Выполнить `GET /api/v1/users/me` с заголовком `X-User-Id: user_A_123`.
-   **Проверки:** Убедиться, что возвращается 200 и объект с полем `id: 'user_A_123'` (и при наличии — `username`, `avatarUrl`).

-   \[ \] Подтверждено, что `GET` запросы отдают корректный статус `userVote` для разных пользователей.
