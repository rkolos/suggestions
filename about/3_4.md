# TASK-3.4: API Комментариев и Модерации

## Контекст и цель задачи

Основное приложение (Web UI) должно предоставлять модераторам интерфейс для управления черным списком пользователей (бан/разбан) и ведения внутренних обсуждений (Team Chat) под каждым предложением. Также админы могут оставлять через Web UI публичные ответы, которые бот должен транслировать в Discord.

Цель этой задачи — обернуть доменные сервисы `CommentsService` и `BansService` (из TASK-2.5) в HTTP-контроллеры, обеспечив валидацию входных данных и строгую проверку `X-Company-Id`.

## Что нужно сделать разработчику (Action Items)

### 1\. Подготовка DTO (Data Transfer Objects)

С использованием `class-validator` создать следующие классы:

-   `CreateCommentDto`:
    
    -   `body`: обязательная строка (не пустая).
    -   `isInternal`: опциональное логическое поле (по умолчанию `true`, так как чаще всего из админки пишут во внутренний чат).
    -   `authorId`: ID автора комментария. Берётся из заголовка **`X-User-Id`** (в DTO может быть опциональным, если контроллер подставляет значение из заголовка).
-   `BanUserDto`:
    
    -   `userId`: обязательная строка (Discord ID пользователя, которого нужно забанить).

### 2\. Реализация `BansController` (API Модерации)

-   Создать контроллер с роутом **`@Controller('api/v1/suggestions/bans')`**. Опционально поддерживать алиас `/api/v1/suggestions/banned-users` для тех же операций (GET/POST/DELETE).
-   Применить глобальный гард `@UseGuards(CompanyIdGuard)`.
-   **Эндпоинты:**
    
    -   `GET /`: Принимает `@CurrentCompany() companyId` и параметры пагинации (query). Возвращает список забаненных юзеров для этой компании (вызов `BansService.getBannedUsers`).
    -   `POST /`: Принимает `@CurrentCompany() companyId` и `@Body() body: BanUserDto`. Вызывает метод `banUser`. Если юзер уже в бане, возвращает безопасный ответ (например, HTTP 409 Conflict или просто 200 OK, в зависимости от выбранной ранее стратегии).
    -   `DELETE /:userId`: Принимает `@CurrentCompany() companyId` и `@Param('userId') userId`. Вызывает метод `unbanUser` (снимает блокировку).

### 3\. Реализация `CommentsController` (API Комментариев)

Для логического соответствия REST API комментарии лучше сделать вложенным ресурсом предложений.

-   Создать контроллер с роутом `@Controller('api/v1/suggestions/:suggestionId/comments')`.
-   Применить глобальный гард `@UseGuards(CompanyIdGuard)`.
-   **Эндпоинты:**
    
    -   `GET /`: Принимает `@CurrentCompany() companyId`, `@Param('suggestionId') suggestionId` и параметры пагинации. Вызывает `CommentsService.findBySuggestionId`.
    -   `POST /`: Принимает `@CurrentCompany() companyId`, `@Param('suggestionId') suggestionId` и `@Body() body: CreateCommentDto`.
        
        -   Вызывает `CommentsService.create`.
        -   Важно: если передан флаг `isInternal: false`, доменный сервис должен сгенерировать событие (Event Emitter), чтобы Discord-бот перехватил его и отправил ответ в публичную ветку.

### 4\. Документация и Обработка ошибок

-   Убедиться, что при запросе комментариев для несуществующего предложения (или предложения чужой компании) возвращается `404 NotFoundException`.
-   (Опционально) Покрыть новые контроллеры декораторами `@nestjs/swagger` для генерации документации.

## Критерии выполнения (Definition of Done)

-   \[ \] Созданы контроллеры `BansController` и `CommentsController`.
-   \[ \] Роуты строго защищены `CompanyIdGuard` (невозможно получить чужие комментарии или забанить юзера в чужой компании).
-   \[ \] Валидация DTO не пропускает пустые комментарии или запросы без `userId`.
-   \[ \] При создании публичного комментария (`isInternal: false`) корректно отрабатывает цепочка вызовов вплоть до генерации доменного события.
-   \[ \] Модераторы могут добавлять и удалять пользователей из черного списка через REST API.
