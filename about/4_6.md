# TASK-4.6: Обработка кнопок голосования (Upvote / Downvote)

## Контекст и цель задачи

Пользователи в Discord должны иметь возможность голосовать за опубликованные предложения, не покидая мессенджер. Для этого под каждым Embed-сообщением с идеей должны располагаться интерактивные кнопки (Upvote / Downvote).

Это самая высоконагруженная часть интерфейса: пользователи могут нажимать на кнопки очень быстро (спамить кликами). Цель этой задачи — добавить кнопки к публикуемым сообщениям, перехватить нажатия на них, защититься от спама с помощью Redis и передать запрос в `VotesService`, чтобы после транзакции обновить счетчики на самих кнопках.

## Что нужно сделать разработчику (Action Items)

### 1\. Добавление кнопок к сообщениям (в `DiscordPublishService`)

В методе публикации из TASK-4.4 необходимо добавить `ActionRowBuilder` с двумя кнопками под Embed-сообщением:

-   **Кнопка Upvote:** \* Style: `Primary` или `Success`.
    
    -   Custom ID: `vote_up_{suggestionId}` (где `{suggestionId}` — ID публикуемого предложения).
    -   Label: содержит иконку/эмодзи (👍) и начальный счетчик (например, "0").
-   **Кнопка Downvote:**
    
    -   Style: `Danger` или `Secondary`.
    -   Custom ID: `vote_down_{suggestionId}`.
    -   Label: содержит иконку/эмодзи (👎) и начальный счетчик.

Эти кнопки должны отправляться в массиве `components` вместе с `embeds` при создании и редактировании сообщений. **При статусе `DUPLICATE`:** при обновлении Embed кнопки голосования **удаляются** (ActionRow с кнопками не передаётся или передаётся пустым), чтобы пользователи не могли голосовать за дубликат (см. TASK-4.4).

### 2\. Создание обработчика кнопок (Button Interaction Listener)

-   В модуле `DiscordModule` создать слушатель для взаимодействия с кнопками (Button Interaction).
-   Извлечь тип голоса (`up` или `down`) и `suggestionId` из `interaction.customId`.
-   **Применить маппинг:** Убедиться, что обработчик защищен перехватчиком из TASK-4.2 (мы должны точно знать `companyId` сервера, на котором нажали кнопку).

### 3\. Защита от спама (Rate Limiting)

Перед вызовом базы данных необходимо реализовать Debounce/Rate Limit:

-   Использовать Redis (например, через `CacheModule` или кастомный сервис).
-   Сформировать ключ кэша: `vote_rate_limit:${companyId}:${userId}:${suggestionId}`.
-   Если ключ существует, немедленно ответить пользователю скрытым (Ephemeral) сообщением: _"Пожалуйста, подождите пару секунд перед повторным голосованием"_ (или просто проигнорировать клик).
-   Если ключа нет, создать его со сроком жизни (TTL) 2-3 секунды.

### 4\. Интеграция с ядром (Toggle Engine)

Внутри обработчика кнопки вызвать логику, написанную в TASK-2.3:

1.  Выполнить ленивую синхронизацию профиля пользователя (сохранить `interaction.user.id` и `username` в таблицу `users`).
2.  Проверить `BansService.isBanned` (из TASK-2.5). Если юзер в бане — отклонить взаимодействие скрытым сообщением.
3.  Вызвать `VotesService.toggleVote(companyId, userId, suggestionId, type)`.
4.  Получить из сервиса новые актуальные значения счетчиков (например, `{ upvotes: 15, downvotes: 3 }`).

### 5\. Обновление UI (Message Update)

-   После успешного пересчета голосов в БД необходимо обновить само сообщение в Discord, чтобы все пользователи увидели новые цифры.
-   В Discord API для этого используется метод `interaction.update(...)`.
-   Сгенерировать новый `ActionRow` с обновленными лейблами на кнопках (например, "👍 15" и "👎 3") и передать их в метод обновления.

## Критерии выполнения (Definition of Done)

-   \[ \] Под каждым опубликованным в Discord предложением отображаются две кнопки голосования.
-   \[ \] При нажатии на кнопку вызывается транзакционный метод `VotesService.toggleVote`.
-   \[ \] Реализован Rate Limit через Redis, не позволяющий одному пользователю пробить БД потоком быстрых кликов.
-   \[ \] Пользователи в блэклисте (Banned) не могут голосовать (получают ошибку).
-   \[ \] Сразу после нажатия кнопки (и успешной транзакции) счетчики на кнопках в Discord визуально обновляются без видимых задержек.
