# TASK-0.1: Утверждение технологического стека

## Контекст и цель задачи

Перед началом написания кода необходимо окончательно зафиксировать технологический стек микросервиса **Suggestions**. Это обеспечит единое понимание архитектуры всеми участниками команды, предотвратит конфликты версий и задаст стандарт для развертывания инфраструктуры.

Данная задача носит архитектурно-документационный характер: разработчику необходимо перенести эти стандарты в репозиторий проекта, чтобы они стали "законом" для дальнейшей разработки.

## Утвержденный технологический стек

Ниже приведен список технологий, которые **обязательны** к использованию в данном микросервисе, с обоснованием выбора:

### 1\. Core (Ядро приложения)

-   **Среда выполнения:** Node.js (LTS версия, рекомендуется `v20.x`).
-   **Язык программирования:** TypeScript (`v5.x`). Обязательно использование режима `strict: true` для предотвращения ошибок типов на этапе компиляции.
-   **Фреймворк:** NestJS (`v10.x`).
    
    -   _Обоснование:_ Обеспечивает строгую модульную архитектуру (out-of-the-box), внедрение зависимостей (DI) и отлично подходит для реализации паттернов Domain-Driven Design (DDD).

### 2\. Данные и Хранение

-   **Основная База Данных:** PostgreSQL (`v15.x` или выше).
    
    -   _Обоснование:_ Надежное хранение реляционных данных, поддержка строгих ограничений (например, уникальные индексы для защиты от накрутки голосов) и JSONB-полей для гибких настроек компаний.
-   **ORM (Object-Relational Mapping):** Prisma ORM.
    
    -   _Обоснование:_ Лучшая типизация на рынке, удобный механизм миграций и интуитивно понятный синтаксис схем (`schema.prisma`).
-   **Кэширование и Очереди:** Redis (`v7.x`) и **BullMQ** (пакет `@nestjs/bullmq`).
    
    -   _Обоснование:_ Redis критически важен для Rate Limiting (защита кнопок голосования в Discord от спама) и кэширования. BullMQ обеспечивает гарантированную доставку фоновых задач (retries), изоляцию тяжелых операций (синхронизация с AI, публикация в Discord, ленивая синхронизация профилей) от основного потока.

### 3\. Интеграции

-   **Discord API:** `discord.js` (`v14.x`).
    
    -   _Обоснование:_ Наиболее стабильная и поддерживаемая библиотека. Строго обязательно использование модуля `ShardingManager` из этой библиотеки для обеспечения масштабируемости SaaS-решения на тысячи серверов.

## Что нужно сделать разработчику (Action Items)

1.  **Создать базовую документацию в репозитории:**
    
    -   Создать файл `TECH_STACK.md` (или соответствующий раздел в основном `README.md` пустого репозитория).
    -   Перенести туда список вышеуказанных технологий с указанием мажорных версий. Версии в `package.json` фиксировать через caret (`^`), например `^10.x`, `^14.x`; лок-файл (`package-lock.json` или `pnpm-lock.yaml`) обеспечит идентичность сборок.
    -   **Политика версий:** В `TECH_STACK.md` зафиксировать, что допустимы минорные обновления внутри мажора (caret `^`). Проверка согласованности версий в CI осуществляется через lockfile (без отдельной проверки `engines` в DoD).
2.  **Зафиксировать версию Node.js:**
    
    -   Создать в корне проекта файл `.nvmrc` и записать туда выбранную LTS версию (например, `20`).
3.  **Настроить ограничения пакетного менеджера (опционально, но рекомендуется):**
    
    -   Выбрать единый пакетный менеджер (рекомендуется `pnpm` или `npm`).
    -   Добавить поле `engines` в `package.json` (после инициализации проекта), чтобы ограничить версию Node.js и пакетного менеджера для всех разработчиков.

## Критерии выполнения (Definition of Done)

-   \[ \] В корневом репозитории микросервиса создан файл `.nvmrc` с указанием версии Node.js.
-   \[ \] В репозитории присутствует файл `README.md` (или `TECH_STACK.md`), в котором явно перечислены: NestJS, TypeScript, PostgreSQL, Prisma, Redis, BullMQ и discord.js, и зафиксирована политика версий (caret, проверка в CI через lockfile).
-   \[ \] (Опционально) В `package.json` настроен блок `"engines"`, фиксирующий версии Node и выбранного пакетного менеджера.
-   \[ \] Выбранный стек согласован с Team Lead / Архитектором проекта (поставлен апрув на этот документ или соответствующий Pull Request).
