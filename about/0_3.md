# TASK-0.3: Стандарты кода и инструменты контроля качества

## Контекст и цель задачи

Поскольку микросервис закладывается как фундамент для масштабируемого SaaS-решения, качество кода должно контролироваться автоматически. Человеческий фактор на код-ревью нужно свести к минимуму: форматирование, стилистические ошибки и базовые опечатки должны отлавливаться еще до создания коммита.

Эта задача описывает настройку линтеров, форматтеров и Git-хуков (pre-commit hooks).

## Требуемые инструменты и стандарты

### 1\. ESLint (Линтер)

Основа контроля качества TypeScript-кода.

-   **База:** Использовать стандартный конфиг, который генерируется при создании проекта NestJS (`@nestjs/eslint-plugin`).
-   **Ужесточение (Strict Rules):**
    
    -   Запрет на использование `any` (`@typescript-eslint/no-explicit-any`: 'error').
    -   Запрет на неиспользуемые переменные (`@typescript-eslint/no-unused-vars`: 'error').
    -   Обязательное указание типов возвращаемых значений для всех методов контроллеров и сервисов, не помеченных модификатором `private` или `protected` (т. е. для всех публичных методов). **Исключений нет:** геттеры в DTO, утилитные методы и тестовые хелперы также обязаны иметь явный тип возвращаемого значения.

### 2\. Prettier (Форматтер)

Единый стандарт форматирования кода. Избавляет от споров про табы/пробелы и кавычки.

-   **Конфигурация (Пример):**
    
    -   `singleQuote: true`
    -   `trailingComma: 'all'`
    -   `printWidth: 100`
    -   `tabWidth: 2`
-   **Интеграция:** Должен работать в связке с ESLint (`eslint-config-prettier`, `eslint-plugin-prettier`), чтобы линтер не ругался на форматирование.

### 3\. Husky & lint-staged (Git Hooks)

Код, который не проходит проверки ESLint или Prettier, не должен попадать в историю Git.

-   **Husky:** Утилита для управления Git-хуками.
-   **lint-staged:** Запускает линтер и форматтер **только** для тех файлов, которые добавлены в индекс (staged). Это ускоряет процесс коммита.

### 4\. Conventional Commits (Стандарт коммитов)

Единый формат сообщений коммитов позволяет в будущем автоматически генерировать Changelog и определять версии (SemVer).

-   **Инструмент:** `@commitlint/cli` и `@commitlint/config-conventional`.
-   **Правило:** Сообщения должны быть вида `тип(скоуп): описание`.
    
    -   _Примеры:_ `feat(suggestions): add official post toggle`, `fix(discord): resolve sharding crash`, `chore: update dependencies`.

## Что нужно сделать разработчику (Action Items)

1.  **Настроить ESLint и Prettier:**
    
    -   Убедиться, что в проекте есть `.eslintrc.js` и `.prettierrc`.
    -   Добавить жесткие правила на `any` и неиспользуемые переменные.
    -   Убедиться, что команды `npm run lint`, `npm run format` и `npm run format:check` работают корректно. Скрипт `format:check` (например, `"format:check": "prettier --check ."`) используется в CI для проверки форматирования без записи файлов.
2.  **Внедрить Husky и lint-staged:**
    
    -   Выполнить `npx husky install` и добавить скрипт `prepare` в `package.json`.
    -   Настроить `lint-staged` в `package.json` для прогона ESLint и Prettier по `*.ts` файлам.
    -   Создать хук `pre-commit`, который вызывает `npx lint-staged`.
3.  **Внедрить проверку коммитов (Commitlint):**
    
    -   Установить commitlint.
    -   Создать файл конфигурации `commitlint.config.js`.
    -   Создать хук `commit-msg`, который запускает `npx --no -- commitlint --edit ${1}`.

## Критерии выполнения (Definition of Done)

-   \[ \] В проекте настроены ESLint и Prettier, конфликты между ними разрешены (Prettier отвечает за стиль, ESLint за логику).
-   \[ \] Папка `.husky` добавлена в кодовую базу (в ней лежат хуки `pre-commit` и `commit-msg`).
-   \[ \] При попытке сделать коммит с синтаксической ошибкой или плохим форматированием, процесс прерывается и выводится ошибка линтера.
-   \[ \] При попытке сделать коммит с сообщением "fixed some stuff" (не по стандарту Conventional Commits) процесс прерывается. Коммит проходит только при сообщении формата `fix: ...` или `feat: ...`.
