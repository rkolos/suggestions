# TASK-2.3: Механика голосования (Toggle Engine)

## Контекст и цель задачи

Голосование за предложения — одна из самых высоконагруженных частей системы. Пользователи взаимодействуют с кнопками в Discord, и каждое нажатие должно либо добавлять голос, либо снимать его (если пользователь нажал ту же кнопку повторно), либо изменять его (если он передумал и нажал противоположную кнопку).

Цель этой задачи — реализовать `VotesService`, который будет инкапсулировать эту логику ("Toggle-механику") с использованием транзакций базы данных Prisma. Это защитит нас от рассинхронизации данных и нарушения уникального индекса `[userId, suggestionId]`, заложенного в схеме БД.

_Архитектурное ограничение: этот сервис занимается только базой данных. Защита от спама (Rate Limit / Debounce) будет реализована позже на уровне контроллеров или слушателей Discord-событий._

## Что нужно сделать разработчику (Action Items)

### 1\. Инициализация модуля

-   В директории `src/modules/votes/` создать `VotesModule` и `VotesService`.
-   Импортировать `PrismaModule` (или использовать глобальный).
-   Импортировать `SuggestionsModule` (опционально, если нужна проверка статуса предложения).

### 2\. Реализация метода `toggleVote`

Создать метод `toggleVote(companyId: string, userId: string, suggestionId: string, type: 1 | -1)`. Логика внутри метода должна выполняться в рамках одной транзакции (используя интерактивные транзакции Prisma `$transaction` или последовательные запросы с обработкой ошибок).

**Алгоритм (Toggle Engine):**

1.  **Проверка предложения:** Убедиться, что предложение с `suggestionId` существует, принадлежит указанному `companyId` и находится в статусе, допускающем голосование. Голосование разрешено **только** в статусах: **`OPEN`, `PLANNED`, `IN_PROGRESS`**. В статусах `NEW`, `DUPLICATE`, `REJECTED`, `COMPLETED`, `CLOSED` голосование запрещено.
2.  **Поиск текущего голоса:** Попытаться найти запись в таблице `votes` по уникальному ключу `[userId, suggestionId]`.
3.  **Разрешение состояния (Toggle):**
    
    -   **Сценарий А (Голоса нет):** Выполнить `INSERT` нового голоса с переданным `type`.
    -   **Сценарий Б (Голос есть, `type` совпадает):** Пользователь повторно нажал ту же кнопку. Выполнить `DELETE` этого голоса (снятие голоса).
    -   **Сценарий В (Голос есть, `type` отличается):** Пользователь поменял свое мнение (с +1 на -1 или наоборот). Выполнить `UPDATE` записи, заменив `type`.
4.  **Агрегация новых метрик:** \* Подсчитать актуальное количество `upvotes` (где `type = 1`) и `downvotes` (где `type = -1`) для данного предложения после изменения.
    
    -   Метод должен возвращать объект с новыми значениями (например, `{ upvotes: 10, downvotes: 2, userVote: 1 | -1 | null }`). Эти данные понадобятся Discord-боту, чтобы немедленно перерисовать кнопки.

### 3\. Обработка ошибок (Race Conditions)

-   В случае параллельных запросов от одного пользователя Prisma может выбросить ошибку нарушения уникального ограничения (`P2002`).
-   `VotesService` не должен обрабатывать эту ошибку напрямую (отдавать 500) — она должна корректно перехватываться глобальным `ExceptionFilter` (из TASK-1.7), который вернет 409 Conflict, что заблокирует параллельную накрутку.

## Критерии выполнения (Definition of Done)

-   \[ \] Создан `VotesService` с методом `toggleVote`.
-   \[ \] Логика метода строго покрывает три сценария: добавление, удаление (toggle off) и переключение (смена мнения) голоса.
-   \[ \] Метод проверяет принадлежность предложения к `companyId` (защита Multi-tenancy).
-   \[ \] Метод возвращает актуальное состояние счетчиков после операции, чтобы клиент (Web UI или Discord) мог моментально обновить интерфейс.
-   \[ \] База данных надежно защищает от двойного голосования одного юзера (благодаря уникальному индексу, добавленному в TASK-1.6).
