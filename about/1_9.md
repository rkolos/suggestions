# TASK-1.9: Системный пользователь и Seed-данные

## Контекст и цель задачи

В ряде сценариев (TASK-2.4 — слияние дубликатов, технические комментарии от имени системы) требуется автор с фиксированным идентификатором **`"system"`**. Запись с таким `id` должна существовать в таблице `users`, чтобы внешние ключи (например, `comments.authorId`) оставались валидными.

Цель этой задачи — зафиксировать способ создания и хранения системного пользователя, при необходимости добавить базовый Seed для разработки и тестов, и отразить конвенцию в API-документации (suggestions-api), чтобы фронтенд и интеграции знали о зарезервированном `author.id`.

## Что нужно сделать разработчику (Action Items)

### 1. Конвенция системного пользователя

-   Зарезервированный идентификатор: **`"system"`** (строка). Используется как `authorId` для технических комментариев (например, «Идея объединена с [ID]» при слиянии в TASK-2.4).
-   Запись в таблице `users`: должна существовать для каждой компании или глобально (один системный пользователь на весь инстанс). Рекомендация: **один глобальный** пользователь с `id = "system"` (без привязки к companyId, если таблица users общая), либо создание при первом обращении (Lazy Create) в контексте компании — в зависимости от схемы БД (см. TASK-1.5, 1.6).
-   Поля: минимум `id`, при необходимости `username: "System"`, `avatarUrl: null` или заглушка. Остальные поля — по умолчанию.

### 2. Создание системного пользователя (Seed или Lazy Create)

Выбрать и реализовать один из подходов:

-   **Вариант A — Seed:** добавить в Prisma seed-скрипт (`prisma/seed.ts` или аналог) вставку пользователя с `id: "system"`. Запуск seed при первом развертывании или по команде `npx prisma db seed`.
-   **Вариант B — Lazy Create:** в сервисе, который впервые нуждается в системном пользователе (например, `CommentsService` при создании комментария от имени системы в TASK-2.4), перед вставкой комментария проверить наличие пользователя с `id = "system"` и при отсутствии создать запись (upsert или `findFirst` + `create`).

Документировать выбранный вариант в README или в комментариях к коду.

### 3. Опциональный Seed для разработки и тестов

-   При необходимости добавить в seed создание тестовой компании (CompanyConfig) и тестовых пользователей для локальной разработки и E2E (см. TASK-6.1). Не обязательно для production; при использовании — хранить seed-данные только в dev/staging или за флагом.

### 4. Отражение в API-документации

-   В suggestions-api (например, в [02-models.md](../suggestions-api/02-models.md) или в разделе «Зарезервированные значения») указать: автор комментария (и при необходимости предложения) может иметь **`author.id === "system"`** — технический автор для системных сообщений (merge, уведомления и т.д.). Формат ответа для такого автора: `{ "id": "system", "username": "System", "avatar_url": null, "isSystem": true }` (если в API введено поле `isSystem`).

## Критерии выполнения (Definition of Done)

-   [ ] Зафиксирована конвенция: идентификатор системного пользователя `"system"`.
-   [ ] Реализовано создание записи пользователя `system` (через Seed или Lazy Create).
-   [ ] При выполнении сценариев, требующих автора "system" (например, комментарий при слиянии в TASK-2.4), запись в БД существует и FK не нарушаются.
-   [ ] В suggestions-api добавлено описание зарезервированного `author.id = "system"` (и при необходимости `isSystem` в ответах).
