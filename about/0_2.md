# TASK-0.2: Утверждение архитектурных паттернов

## Контекст и цель задачи

Микросервис **Suggestions** является частью более крупной экосистемы (SaaS-платформы). Чтобы код не превратился в монолит и легко масштабировался, необходимо на старте определить жесткие правила игры: как сервисы общаются друг с другом, как изолируются данные клиентов и как структурируется код.

Данная задача, как и предыдущая, направлена на фиксацию архитектурных договоренностей в кодовой базе проекта до начала написания бизнес-логики.

## Ключевые архитектурные паттерны

Разработчик обязан придерживаться следующих паттернов при проектировании и написании кода:

### 1\. Trusted Internal API (API Gateway Offloading)

Микросервис работает в защищенном контуре и **не занимается** проверкой JWT-токенов, паролей или ролей пользователей (Admin/Manager/User).

-   **Правило:** Вся маршрутизация идет через основной API Gateway (основное приложение), который проводит аутентификацию и авторизацию.
-   **Реализация:** Основное приложение проксирует запросы к микросервису, пробрасывая проверенные данные через HTTP-заголовки. Главные заголовки, на которые опирается микросервис:
    
    -   `X-Company-Id` (обязателен почти для всех роутов) — идентификатор SaaS-клиента.
    -   `X-User-Id` (опционален, нужен для действий от лица пользователя) — Discord ID юзера.
-   **Следствие:** Если микросервис получает запрос с заголовком `X-Company-Id` на удаление сущности, он доверяет запросу и выполняет его, не проверяя, есть ли у пользователя на это права.

### 2\. Multi-tenancy (Строгая изоляция данных)

Поскольку приложение обслуживает множество серверов (SaaS), данные разных клиентов лежат в одной базе данных, но должны быть логически изолированы.

-   **Правило:** Ни один запрос к базе данных (select, update, delete), касающийся бизнес-сущностей, не должен выполняться без условия `where: { companyId: '...' }`.
-   **Реализация:** Заголовок `X-Company-Id` должен перехватываться на уровне NestJS Guard/Interceptor и передаваться контекстом во все сервисы и Prisma-запросы.

### 3\. Domain-Driven Design (Модульность / DDD)

Код должен быть разделен на независимые предметные области (домены), а не сгруппирован по техническому признаку (папка со всеми контроллерами, папка со всеми сервисами — **запрещены**).

-   **Правило:** Каждый домен инкапсулирует свои контроллеры, сервисы и интерфейсы.
-   **Структура (пример):**
    
    -   `src/modules/suggestions/` — модуль предложений.
    -   `src/modules/votes/` — модуль голосования.
    -   `src/modules/discord/` — модуль интеграции с ботом.
    -   `src/common/` — глобальные Guards, фильтры ошибок, утилиты.

### 4\. Discord Sharding (Масштабирование бота)

Бот будет обслуживать тысячи серверов (Guilds). Стандартный запуск `Client.login()` не выдержит нагрузки и упрется в лимиты Gateway Discord.

-   **Правило:** Точка входа в приложение (или отдельный скрипт запуска бота) должна использовать `ShardingManager` из библиотеки `discord.js`.
-   **Реализация:** Основной процесс (Manager) порождает дочерние процессы (Шарды). Каждый шард — это **полное NestJS-приложение** (HTTP + Discord): любой инстанс может обработать и API-запрос, и событие Discord своего шарда. Это упрощает масштабирование.
