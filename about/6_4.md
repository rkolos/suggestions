# TASK-6.4: Сценарий C - Массовые операции, Дубликаты и AI (Edge Cases)

## Контекст и цель задачи

Третий и финальный Smoke-сценарий покрывает сложные операции, которые обычно вызывают больше всего багов: работу с массивами данных (Bulk API) и интеграцию со сторонними сервисами (AI-микросервис).

Мы должны убедиться, что транзакции массового обновления работают корректно, слияние дубликатов правильно связывает записи, а наше приложение не падает, если AI-сервис вдруг ответил 500 ошибкой (Graceful Degradation).

## Что нужно сделать разработчику (Action Items)

### 1\. Подготовка тестового блока и данных

-   Добавить блок `describe('Scenario C: Bulk & AI Flow', () => { ... })`.
-   В хуке `beforeAll` этого блока (или в первых шагах) создать **три** новых предложения от лица обычного пользователя. Сохранить их ID в переменные (например, `sug1`, `sug2`, `sug3`).

### 2\. Шаг 1: Массовое изменение статуса (Bulk Status)

-   **Действие:** Выполнить **`POST /api/v1/suggestions/bulk/status`** от лица администратора.
-   **Payload:** `{ "ids": [sug1, sug2], "status": "PLANNED" }`.
-   **Проверки:**
    
    -   Статус `201 Created` (или `200 OK`).
    -   Выполнить `GET /api/v1/suggestions` и убедиться, что у предложений `sug1` и `sug2` статус изменился на `PLANNED`, а у `sug3` остался `NEW`.

### 3\. Шаг 2: Успешный запрос к AI (Поиск дубликатов)

В E2E тестах мы не должны стучаться в реальный AI-сервис. В тестовом окружении **`ConfigService`** должен подменять `AI_SERVICE_URL` на **фиксированный тестовый URL** (например, `http://ai-mock`), который затем перехватывается библиотекой **`nock`**.

-   **Подготовка:** Настроить nock на этот тестовый URL так, чтобы при POST-запросе на `/rag/search` возвращался массив `[sug1]`.
-   **Действие:** Выполнить `POST /api/v1/suggestions/similar`.
-   **Payload:** `{ "text": "Текст похожий на sug1" }`.
-   **Проверки:**
    
    -   Статус `200 OK` или `201 Created`.
    -   Ответ должен быть массивом из одного элемента.
    -   Этот элемент — полный объект предложения `sug1` (включая его `title` и счетчики голосов, а не просто голый ID).

### 4\. Шаг 3: Слияние дубликатов (Bulk Merge)

-   **Действие:** Допустим, админ решил, что `sug3` — это дубликат `sug1`. Выполнить **`POST /api/v1/suggestions/bulk/merge`** от лица администратора.
-   **Payload:** `{ "sourceIds": [sug3], "targetId": sug1 }`.
-   **Проверки:**
    
    -   Статус `201 Created` (или `200 OK`).
    -   Сделать запрос `GET /api/v1/suggestions/sug3` (запросить дубликат).
    -   Убедиться, что его `status` равен `DUPLICATE`, а поле `mergedIntoId` равно `sug1`.

### 5\. Шаг 4: Падение AI-сервиса (Graceful Degradation)

Проверяем устойчивость приложения к сбоям внешней инфраструктуры.

-   **Подготовка:** Настроить nock так, чтобы запрос к AI-сервису возвращал `500 Internal Server Error` или таймаут.
-   **Действие:** Повторить запрос `POST /api/v1/suggestions/similar`.
-   **Проверки:**
    
    -   **Критически важно:** Наш эндпоинт **НЕ** должен вернуть 500 ошибку.
    -   Статус ответа нашего API должен быть `200 OK` или `201 Created`.
    -   В теле ответа должен прийти пустой массив `[]` (приложение элегантно "сдеградировало", сообщив, что дубликатов нет, раз AI недоступен).

## Критерии выполнения (Definition of Done)

-   \[ \] Сценарий C успешно проходит все шаги.
-   \[ \] Bulk API корректно обрабатывает массивы ID и обновляет сразу несколько записей в БД.
-   \[ \] API слияния (`merge`) корректно проставляет внешние ключи `mergedIntoId` и меняет статус на `DUPLICATE`.
-   \[ \] Доказана отказоустойчивость: при падении AI-интеграции основное приложение продолжает обслуживать пользователей.
