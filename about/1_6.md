# TASK-1.6: Схема БД (Часть 2: Бизнес-сущности)

## Контекст и цель задачи

В предыдущей задаче мы заложили фундамент (компании и пользователи). Теперь необходимо описать в `schema.prisma` основные сущности предметной области: предложения (Suggestions), голоса (Votes), комментарии (Comments) и список забаненных пользователей (BannedUsers).

Цель этой задачи — спроектировать связи между таблицами, обеспечить каскадное удаление (onDelete: Cascade) там, где это необходимо, и защитить данные от накруток с помощью уникальных составных индексов. Согласно нашим стандартам, примеры кода Prisma опущены — разработчику нужно перенести это описание в синтаксис `schema.prisma` самостоятельно.

## Что нужно сделать разработчику (Action Items)

### 1\. Описание модели Suggestion (Предложение)

Создать модель `Suggestion` (рекомендуемое имя таблицы: `suggestions`). Это центральная сущность системы.

**Требуемые поля и связи:**

-   `id` — первичный ключ (строка). Идентификаторы должны генерироваться на уровне приложения с префиксом (например, `sug_abc123`).
-   `companyId` — внешний ключ (UUID), ссылающийся на `CompanyConfig`. **Связь:** при удалении компании предложения должны удаляться каскадно.
-   `authorId` — внешний ключ (строка), ссылающийся на `User` (создателя).
-   `source` — перечисление (Enum `SuggestionSource`): `DISCORD` или `WEB`. По умолчанию `WEB`.
-   `title` — строка (заголовок предложения).
-   `description` — текст (описание).
-   `category` — строка (идентификатор выбранной категории).
-   `isOfficial` — логическое поле (по умолчанию `false`).
-   `status` — перечисление (Enum `SuggestionStatus`): `NEW`, `OPEN`, `DUPLICATE`, `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `REJECTED`. По умолчанию `NEW`. _(В REST-ответах статусы отдаются в формате Title Case, см. API Spec; маппинг выполняется на уровне контроллеров.)_
-   `slug` — строка для SEO-friendly URL. **Уникальность:** задать составной уникальный индекс `@@unique([companyId, slug])`, чтобы slug был уникален в рамках компании.
-   `discordMessageId` — опциональная строка (ID опубликованного Embed в канале).
-   `discordThreadId` — опциональная строка (ID ветки обсуждения).
-   `mergedIntoId` — опциональная строка (ID оригинального предложения, если текущее помечено как дубликат). **Связь:** ссылается на эту же таблицу `Suggestion` (self-relation).
-   `ai_summary` — опциональная строка (текст для AI-блока; заполняется асинхронно или по запросу).
-   `type` — опциональная строка (например `'official_proposal'` для официальных постов).
-   `isPinned` — логическое поле (по умолчанию `false`; для официальных постов — `true`).
-   `createdAt` и `updatedAt` — стандартные временные метки.
-   **Индексы:** создать составной индекс по полям `[companyId, status]` для ускорения выборок списков в админке.

### 2\. Описание модели Vote (Голос)

Создать модель `Vote` (имя таблицы: `votes`). Хранит реестр голосов для реализации механики Toggle-Voting.

**Требуемые поля и связи:**

-   `userId` — внешний ключ, ссылающийся на `User` (каскадное удаление).
-   `suggestionId` — внешний ключ, ссылающийся на `Suggestion` (каскадное удаление).
-   `type` — целое число (`1` для upvote, `-1` для downvote).
-   `createdAt` — дата создания.
-   **КРИТИЧЕСКИ ВАЖНО (Защита от накрутки):** использовать составной первичный ключ **`@@id([userId, suggestionId])`**. Это гарантирует на уровне БД, что один пользователь может оставить только один активный голос за одно предложение.

### 3\. Описание модели Comment (Комментарий)

Создать модель `Comment` (имя таблицы: `comments`). Используется для Team Chat и синхронизации тредов из Discord.

**Требуемые поля и связи:**

-   `id` — первичный ключ (строка, UUID генерируется автоматически).
-   `suggestionId` — внешний ключ, ссылающийся на `Suggestion` (каскадное удаление).
-   `authorId` — внешний ключ, ссылающийся на `User` (каскадное удаление).
-   `body` — текстовое поле (содержимое комментария).
-   `isInternal` — логическое поле (по умолчанию `false`). Если `true`, комментарий виден только в админ-панели (Team Chat) и не публикуется в Discord.
-   `createdAt` и `updatedAt` — стандартные временные метки.

### 4\. Описание модели BannedUser (Блэклист)

Создать модель `BannedUser` (имя таблицы: `banned_users`).

**Требуемые поля и связи:**

-   `companyId` — внешний ключ, ссылающийся на `CompanyConfig` (каскадное удаление).
-   `userId` — строка (Discord ID пользователя). **Рекомендуемая реализация:** хранить `userId` как **String без формальной связи (FK)** с таблицей `User` в Prisma. Это гарантирует, что бан сохранится в системе даже после удаления пользователя из глобального кэша (`users`).
-   `bannedAt` — дата и время выдачи бана (по умолчанию `now()`).
-   **Индексы:** уникальный составной ключ по полям `[companyId, userId]`, чтобы нельзя было забанить одного пользователя дважды в рамках одной компании. Можно использовать это как составной первичный ключ.
