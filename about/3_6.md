# TASK-3.6: Интеграция UI-фичей (Статус голоса и Вложения)

## Контекст и цель задачи

Для того чтобы фронтенд-разработчики могли создать полноценный и интуитивно понятный пользовательский интерфейс (Web UI), базовых CRUD-операций недостаточно. Возникли две критичные потребности:

1.  **Подсветка нажатых кнопок (User Vote State):** Когда пользователь заходит на страницу со списком идей, фронтенду нужно знать, за какие идеи этот конкретный пользователь уже проголосовал, чтобы закрасить кнопки (Upvote/Downvote) в активный цвет.
2.  **Иллюстрация идей (Attachments):** Пользователям необходимо прикреплять референсы, мокапы или скриншоты багов к своим предложениям для большей наглядности.

Цель этой задачи — расширить существующие методы чтения списка предложений и обновить схему базы данных для поддержки массива изображений.

## Что нужно сделать разработчику (Action Items)

### 1\. Чтение состояния голоса (User Vote State)

Необходимо доработать методы `findAll` и `findById` в `SuggestionsService`, а также соответствующие контроллеры `GET /api/v1/suggestions` и `GET /api/v1/suggestions/:id` (из TASK-3.2).

-   **Модификация контроллера:**
    
    -   Добавить извлечение опционального заголовка `X-User-Id` (например, через декоратор `@CurrentUser()`, если он был реализован в TASK-1.8).
    -   Передать этот `userId` в сервисы `findAll` и `findById` последним аргументом.
-   **Логика в сервисе (Prisma):**
    
    -   Если `userId` передан, при запросе в базу данных необходимо добавить условие для подгрузки голоса этого пользователя: `include: { votes: { where: { userId } } }`.
-   **Маппинг ответа (Serialization):**
    
    -   При формировании JSON-ответа на фронтенд, пробежаться по массиву предложений и для каждого добавить виртуальное поле `userVote` (типа `1 | -1 | null`).
    -   Поле `votes` (массив из БД) при этом лучше скрыть из финального ответа, чтобы не засорять сеть.

### 2\. Поддержка вложений (Attachments / Скриншоты)

Необходимо научить систему сохранять ссылки на картинки, прикрепленные к предложениям.

-   **Доработка БД (Схема Prisma):** \* Открыть файл `schema.prisma`.
    
    -   Добавить в модель `Suggestion` (созданную в TASK-1.6) новое поле **`images`** — в Prisma для PostgreSQL строго тип **`String[]`** (массив строк в БД).
    -   Создать и применить миграцию (`npx prisma migrate dev --name add_suggestion_images`).
-   **Доработка DTO (Валидация):** \* В классы `CreateSuggestionDto` и `UpdateSuggestionDto` добавить опциональное поле `images`.
    
    -   Типизировать его как массив строк и покрыть декораторами валидации из `class-validator`: `@IsOptional()`, `@IsArray()`, `@IsUrl({}, { each: true })` (чтобы убедиться, что каждый элемент массива — это валидный URL-адрес картинки).
-   **Примечание для MVP:** На данном этапе сам микросервис не должен заниматься процессингом бинарных файлов (multipart/form-data). Предполагается, что фронтенд (или основное приложение) загружает картинки напрямую в S3 хранилище, а в наш REST API передает уже готовые публичные URL-адреса.

## Критерии выполнения (Definition of Done)

-   \[ \] Эндпоинты `GET /suggestions` и `GET /suggestions/:id` корректно обрабатывают заголовок `X-User-Id` и возвращают поле `userVote` для каждой карточки идеи.
-   \[ \] В модель `Suggestion` добавлено поле `images` (массив строк), миграция успешно применена к базе данных.
-   \[ \] Эндпоинты создания (`POST`) и обновления (`PATCH`) предложений принимают и сохраняют валидный массив ссылок на изображения.
-   \[ \] Типы и Swagger-документация (если используется) обновлены с учетом новых полей.
