# TASK-1.1: Инициализация репозитория и NestJS

## Контекст и цель задачи

Все архитектурные решения приняты в Блоке 0. Теперь необходимо создать физический каркас микросервиса. В этой задаче разработчик генерирует базовое приложение NestJS, настраивает TypeScript в максимально строгом режиме и выстраивает правильную структуру папок (Domain-Driven Design).

Эта заготовка станет фундаментом, на который в следующих задачах будут нанизываться подключение к базе данных, Discord-бот и бизнес-логика.

## Что нужно сделать разработчику (Action Items)

### 1\. Генерация проекта

-   Инициализировать новое приложение с помощью Nest CLI:
    
    ```
    npx @nestjs/cli new suggestions-service
    ```
    
-   Выбрать пакетный менеджер, утвержденный в `TASK-0.1` (например, `npm` или `pnpm`).

### 2\. Настройка TypeScript (Строгий режим)

По умолчанию NestJS генерирует достаточно мягкий `tsconfig.json`. Его необходимо ужесточить для предотвращения скрытых багов:

-   Открыть `tsconfig.json`.
-   Убедиться, что в `compilerOptions` установлены следующие флаги:
    
    ```
    "strict": true,
    "noImplicitAny": true,
    "strictNullChecks": true,
    "forceConsistentCasingInFileNames": true,
    "noFallthroughCasesInSwitch": true
    ```
    

### 3\. Очистка Boilerplate-кода и Healthcheck

-   Удалить сгенерированные по умолчанию контроллеры и сервисы из `src/` (например, `app.controller.ts`, `app.service.ts`), если они содержат пример с "Hello World".
-   Создать простой `HealthController` с каноническим путём **`GET /health`**, возвращающий `{ status: 'ok', timestamp: '...' }`. Это понадобится для Docker/Kubernetes probes. **Корень `GET /`** должен возвращать **404 Not Found**; единственный канонический путь для проверки работоспособности — `GET /health`.

### 4\. Создание структуры директорий (DDD)

Сформировать внутри папки `src/` каркас для будущих доменов (создать папки и положить в них `.gitkeep` или пустые модули):

```
src/
├── common/               # Глобальные утилиты: Guards, Filters, Interceptors, Decorators
│   └── prisma/           # PrismaService и PrismaModule (см. TASK-1.4)
├── config/               # Валидация .env и конфигурация приложения
├── modules/              # Бизнес-домены (DDD)
│   ├── suggestions/      # Основной модуль: CRUD предложений
│   ├── votes/            # Модуль механики голосования
│   ├── comments/         # Модуль внутренних комментариев (Team Chat)
│   ├── discord/          # Интеграция с Discord (Шардинг, Commands, Events)
│   ├── ai-integration/   # HTTP-клиенты для RAG и поиска дубликатов
│   ├── companies/        # Настройки конкретных клиентов (CompanyConfig)
│   ├── moderation/       # BansService, блэклист (см. TASK-2.5)
│   └── users/            # UsersService, кэш профилей Discord (см. TASK-5.3; реализуется до Блока 4)
├── app.module.ts         # Корневой модуль (импортирует все модули из modules/)
└── main.ts               # Точка входа
```

### 5\. Интеграция линтеров из Блока 0

-   Убедиться, что настройки из `TASK-0.3` (ESLint, Prettier, Husky, lint-staged) успешно применены к сгенерированному коду.
-   Выполнить `npm run lint` и исправить любые потенциальные ошибки начальной генерации.

## Критерии выполнения (Definition of Done)

-   \[ \] Репозиторий инициализирован, приложение успешно запускается командой `npm run start:dev`.
-   \[ \] В `tsconfig.json` включен режим `"strict": true`.
-   \[ \] Эндпоинт `GET /health` возвращает статус `200 OK` с телом `{ status: 'ok', timestamp: '...' }`. Запрос `GET /` возвращает **404 Not Found**.
-   \[ \] Структура папок в `src/` соответствует архитектуре DDD (разделена на `common`, `config`, `modules/...`).
-   \[ \] Запуск линтера `npm run lint` проходит без единой ошибки и предупреждения.
