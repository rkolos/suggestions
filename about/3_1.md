# TASK-3.1: API Настроек (Config Controller)

## Контекст и цель задачи

Микросервис работает в режиме Multi-tenancy, где каждая компания (арендатор) имеет свои уникальные настройки: список доступных категорий для предложений, ID канала в Discord для публикации, шаблоны уведомлений. Основное приложение (Web UI) должно иметь возможность получать и изменять эти настройки.

Цель этой задачи — создать REST API контроллер, который будет обслуживать эти запросы, опираясь на заголовок `X-Company-Id` (через созданный ранее `CompanyIdGuard`).

## Что нужно сделать разработчику (Action Items)

### 1\. Создание сервиса и DTO

-   Если еще не создан, добавить `CompanyConfigService` (в папку `src/modules/companies/` или `config/`).
-   Этот сервис должен реализовывать два метода, работающих с таблицей `companies_config` через Prisma:
    
    -   `getConfig(companyId: string)` — возвращает конфигурацию или создает дефолтную (пустую), если запись для этой компании еще не существует.
    -   `updateConfig(companyId: string, data: UpdateConfigDto)` — обновляет JSON-поля (категории, шаблоны) и строковые поля (ID канала).
-   Создать `UpdateConfigDto` с использованием `class-validator` (описать типы для массива категорий и объекта шаблонов).

### 2\. Реализация `ConfigController`

-   Создать контроллер с базовым роутом **`@Controller('api/v1/suggestions/config')`** (префикс модуля suggestions; эндпоинты GET / и PUT / дают в итоге `GET /api/v1/suggestions/config` и `PUT /api/v1/suggestions/config`).
-   Применить к контроллеру глобально (на уровне класса) созданный в TASK-1.8 `@UseGuards(CompanyIdGuard)`. Это гарантирует, что ни один эндпоинт не будет вызван без идентификатора компании.

### 3\. Эндпоинт `GET /`

-   Реализовать метод `getConfig(@CurrentCompany() companyId: string)`.
-   Метод должен вызывать сервис и отдавать текущие настройки компании в формате JSON.

### 4\. Эндпоинт `PUT /` (или `PATCH /`)

-   Реализовать метод `updateConfig(@CurrentCompany() companyId: string, @Body() body: UpdateConfigDto)`.
-   Метод должен принимать проверенные через DTO данные, обновлять конфигурацию в БД и возвращать обновленный объект.

### 5. Эндпоинт `GET /defaults` (Reset to Default)

-   **`GET /api/v1/suggestions/config/defaults`:**
    -   Назначение: кнопка «Reset to Default» в настройках (Settings); возвращает дефолтные шаблоны категорий и уведомлений, которые фронт может подставить в форму перед сохранением.
    -   Реализация: метод в `CompanyConfigService` (например, `getDefaultConfig()`), возвращающий константный или конфигурируемый объект дефолтов; контроллер отдаёт его без привязки к компании или с учётом конвенции API (см. suggestions-api 05).
    -   Защита: `CompanyIdGuard` при необходимости (если дефолты общие для всех — роут может быть под тем же контроллером с путём `config/defaults`).

### 6. Эндпоинты только шаблонов уведомлений (опционально)

-   **`GET /api/v1/suggestions/settings/notifications`** и **`PUT /api/v1/suggestions/settings/notifications`:**
    -   Назначение: по контракту API (suggestions-api 05, 07) — отдельные роуты для получения и сохранения только шаблонов уведомлений (без категорий и остальных полей config). Удобно для экрана настроек, где редактируют только уведомления.
    -   Реализация: либо дополнительные методы в том же `ConfigController` (под путём `settings/notifications` через вложенный контроллер или подроут), либо отдельный контроллер; сервис `CompanyConfigService` должен поддерживать чтение/запись только поля шаблонов (notifications). Формат тела — по 02-models и 05-endpoints-duplicates-config.

### 7\. Интеграция с Swagger / OpenAPI (Опционально, но рекомендуется)

-   Использовать декораторы `@ApiTags`, `@ApiOperation`, `@ApiResponse` из `@nestjs/swagger` для документации этих эндпоинтов, чтобы команда фронтенда (или разработчики основного приложения) понимали формат запросов и ответов.

## Критерии выполнения (Definition of Done)

-   \[ \] Создан `ConfigController` и соответствующие DTO с валидацией (`class-validator`).
-   \[ \] Роуты контроллера защищены `CompanyIdGuard`.
-   \[ \] GET-запрос с заголовком `X-Company-Id` возвращает настройки (или дефолтную конфигурацию).
-   \[ \] PUT-запрос успешно обновляет `categories` и `suggestionsChannelId` в БД, и изменения сохраняются при повторном GET-запросе.
-   \[ \] Запросы без `X-Company-Id` или с невалидным телом (Body) отклоняются с **400 Bad Request** в стандартном JSON-формате нашего фильтра исключений.
-   \[ \] Реализован **GET** `/api/v1/suggestions/config/defaults` — возвращает дефолтные шаблоны для «Reset to Default».
-   \[ \] При необходимости реализованы **GET** и **PUT** `/api/v1/suggestions/settings/notifications` — только шаблоны уведомлений (по контракту API).
