# TASK-0.4: Проектирование пайплайнов (CI/CD) и стратегии деплоя

## Контекст и цель задачи

Микросервис не может существовать только на локальной машине разработчика. До написания бизнес-логики нужно четко определить, как приложение будет доставляться на сервер (Production/Staging), как безопасно обновлять схему базы данных (чтобы не поломать работающих Discord-ботов) и как мониторить его работу.

Эта задача описывает конфигурацию Docker, стратегию деплоя миграций Prisma и стандарты логирования.

## Требуемые стандарты и подходы

### 1\. Docker и Контейнеризация

Микросервис должен быть полностью stateless (не хранить состояние в памяти дольше положенного) и поставляться в виде Docker-образа.

-   **Базовый образ:** Использовать легковесные образы (например, `node:20-alpine`).
-   **Multi-stage сборка:** В `Dockerfile` должно быть разделение на этап сборки (установка `devDependencies`, `nest build`, `prisma generate`) и этап продакшена (копирование только скомпилированного кода `dist/` и `node_modules` без dev-зависимостей). Это уменьшит вес финального образа и повысит безопасность.

### 2\. Стратегия деплоя и Миграции БД (Критично!)

Так как мы используем Prisma и Discord Sharding, обновление сервиса должно происходить в строгом порядке, чтобы избежать конфликтов схемы БД.

-   **Правило:** Миграции базы данных (`npx prisma migrate deploy`) должны выполняться **строго ДО** запуска новых контейнеров приложения.
-   **Реализация:** \* Запуск миграций выполняется либо отдельным CI/CD шагом, либо через `init-container` (если используется Kubernetes), либо скриптом `pre-start.sh`, который сначала накатывает миграции, а затем делает `node dist/main.js`.
    
    -   _Запрещено_ использовать `prisma db push` в production-окружении.

### 3\. Логирование (Observability)

Стандартного `console.log` недостаточно для микросервиса, который обслуживает тысячи серверов Discord.

-   **Инструмент:** Использовать библиотеку `pino` (через `nestjs-pino`) или `winston` (через `nest-winston`). Рекомендуется `pino` из-за высокой производительности.
-   **Формат логов:** \* В режиме `development`: Pretty-print (человекочитаемый, цветной текст).
    
    -   В режиме `production`: Строго **JSON-формат**. Это необходимо для автоматического парсинга логов системами вроде ELK (Elasticsearch), Datadog или Grafana Loki.
-   **Контекст логов:** В логах обязательно должен присутствовать контекст (например, `company_id`, `guild_id`, `shard_id`), чтобы можно было отследить путь запроса конкретного клиента.

### 4\. CI/CD Pipeline (Непрерывная интеграция)

Любой Pull Request в основную ветку (main/master) должен проходить автоматические проверки.

-   **Шаги пайплайна (на примере GitHub Actions или GitLab CI):**
    
    1.  `Checkout` кода.
    2.  Установка зависимостей (`npm ci`).
    3.  Проверка линтером (`npm run lint`) и форматтером (`npm run format:check`). Убедиться, что в `package.json` присутствует скрипт `"format:check": "prettier --check ."` (см. TASK-0.3).
    4.  Сборка проекта (`npm run build`).
    5.  Генерация Prisma клиента (`npx prisma generate`).

## Что нужно сделать разработчику (Action Items)

1.  **Создать `Dockerfile` и `.dockerignore`:**
    
    -   Написать multi-stage Dockerfile для продакшен-сборки.
    -   Убедиться, что в `Dockerfile` вызывается `prisma generate`.
2.  **Настроить кастомный логгер:**
    
    -   Установить `nestjs-pino` (или аналог).
    -   Подключить его глобально в `main.ts` вместо стандартного `Logger` от NestJS.
    -   Настроить переключение формата (JSON для продакшена, Pretty для локальной разработки) на основе `process.env.NODE_ENV`.
3.  **Создать конфигурацию CI-пайплайна:**
    
    -   Создать файл `.github/workflows/ci.yml` (если используется GitHub) или `.gitlab-ci.yml`.
    -   Описать базовую джобу (lint + build), чтобы CI загорался "зеленым" при валидном коде.
4.  **Задокументировать стратегию запуска:**
    
    -   Добавить в `README.md` (или `DEPLOYMENT.md`) инструкцию по развертыванию, где капсом выделить необходимость запуска `npx prisma migrate deploy` перед стартом приложения.

## Критерии выполнения (Definition of Done)

-   \[ \] В корне проекта лежит рабочий multi-stage `Dockerfile` (образ собирается без ошибок).
-   \[ \] В проекте настроен кастомный логгер, который пишет логи в JSON при `NODE_ENV=production`.
-   \[ \] Создан файл CI-пайплайна (`.github/workflows/ci.yml`), который прогоняет `lint` и `build`.
-   \[ \] В `README.md` описан алгоритм деплоя, явно указывающий порядок запуска миграций Prisma.
