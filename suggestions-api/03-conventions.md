# Соглашения API

## Пагинация

- **Схема:** offset-based: параметры `page` (номер страницы, с 1) и `limit` (размер страницы).
- **Лимиты по умолчанию:** `limit=20`. **Жёсткий максимум:** `limit` не должен превышать 100. Если клиент передаёт `limit=1000000` или больше — бекенд принудительно ограничивает значение (например `min(requested_limit, 100)`) и возвращает страницу с фактически использованным limit, чтобы избежать перегрузки БД. Рекомендуется в ответе возвращать фактический `limit` (и при необходимости `page`).
- **Ответ:** в теле обязательно поле `total: number` (общее количество записей). Для списков с пагинацией — полная мета-информация: **`{ items: T[], total: number, page: number, limit: number }`** (все четыре поля возвращаются для консистентности).
- **Альтернатива (cursor):** для бесконечной ленты (например комментарии) можно использовать `cursor` + `limit`; в ответе — `nextCursor?: string` (отсутствует или пустая строка, если следующей страницы нет).

## Формат ошибок

Все ошибки API возвращают JSON с единым форматом:

```json
{
  "error": {
    "code": "КОД_ОШИБКИ",
    "message": "Человекочитаемое описание",
    "details": {},
    "timestamp": "2024-01-20T10:00:00Z",
    "path": "/api/v1/suggestions/sug_123"
  }
}
```

Поля `details` (доп. данные, например categoryId, suggestionCount), `timestamp` (ISO 8601) и `path` (путь запроса без хоста) обязательны для единообразия с микросервисом.

**Коды HTTP и code:**

| HTTP | code | Когда |
|------|------|--------|
| 400 | BAD_REQUEST | Невалидные параметры (пустой body, неверный тип, нарушение ограничений: длина категории > 30, шаблон > 500 и т.д.) |
| 401 | UNAUTHORIZED | Отсутствует или невалиден токен/сессия |
| 403 | FORBIDDEN | Недостаточно прав (настройки, бан, официальное предложение) |
| 404 | NOT_FOUND | Ресурс не найден (suggestion, ban, категория по id) |
| 409 | CONFLICT | Конфликт с текущим состоянием: CATEGORY_IN_USE — попытка удалить категорию, в которой есть предложения |

**Пример тела 409 при удалении категории:**

```json
{
  "error": {
    "code": "CATEGORY_IN_USE",
    "message": "Невозможно удалить категорию: в ней есть предложения",
    "details": { "categoryId": "cat_1", "suggestionCount": 5 },
    "timestamp": "2024-01-20T10:00:00Z",
    "path": "/api/v1/suggestions/config"
  }
}
```

## Формат ответа при grouped=true (GET suggestions)

При `GET /api/v1/suggestions?grouped=true` ответ: `{ items: (SuggestionCluster | Suggestion)[], total: number }`.

**Как отличить кластер от одиночного предложения в JSON:**

- Элемент **кластера:** объект с полем `"type": "cluster"` и полями `master`, `children`, `totalDuplicates`. Одиночное предложение не должно содержать `type: "cluster"`.
- Элемент **одиночного предложения:** объект без поля `type` или с `"type": "suggestion"`, структура как у модели Suggestion (id, author, content, metrics, lifecycle, created_at, …).

**Пример элемента-кластера:**

```json
{
  "type": "cluster",
  "master": { "id": "sug_8821", "content": { "title": "..." }, "lifecycle": { "status": "Open" }, ... },
  "children": [
    { "id": "sug_8827", "content": { "title": "..." }, "lifecycle": { "status": "New" }, ... }
  ],
  "totalDuplicates": 1
}
```

**Пример элемента-одиночки:** обычный объект Suggestion (без `type` или с `"type": "suggestion"`).

## Аутентификация и текущий пользователь

- **Идентификация пользователя:** по заголовку `Authorization: Bearer <token>` (JWT или session token). Альтернатива: cookie сессии (например `session_id`). В документации зафиксировать один способ для всех защищённых эндпоинтов.
- **Проксирование через Gateway (Trusted Internal API):** микросервис Suggestions работает за API Gateway. Gateway проверяет токен/сессию и подставляет проверенные заголовки **`X-Company-Id`** и **`X-User-Id`** в запрос к микросервису. Микросервис доверяет этим заголовкам и не проверяет JWT самостоятельно. Все защищённые эндпоинты требуют наличия `X-Company-Id` (и при необходимости `X-User-Id`) в запросе.
- **Текущий пользователь используется для:** автор созданного предложения (POST suggestions), автор комментария в Team Chat (POST comments), проверка прав (Settings, Ban, Official proposal). Бекенд извлекает user id и, при необходимости, роль из заголовка `X-User-Id` (или из токена/сессии на стороне Gateway) и подставляет в `author` при создании ресурсов; эндпоинт GET /me возвращает расширенный контракт с role и permissions (см. [06-endpoints-team-config.md](06-endpoints-team-config.md)#авторизация-и-права-доступа-get-me-проверка-прав).
