# Архитектура микросервиса Suggestions

Документ фиксирует архитектурные паттерны, обязательные к соблюдению при проектировании и разработке микросервиса Suggestions.

---

## 1. Trusted Internal API (API Gateway Offloading)

Микросервис работает в **защищённом контуре** и **не выполняет** проверку JWT-токенов, паролей или ролей пользователей (Admin/Manager/User).

### Правило

Вся маршрутизация идёт через основной **API Gateway** (основное приложение платформы). Gateway проводит аутентификацию и авторизацию, после чего проксирует запросы к микросервису, передавая проверенные данные через HTTP-заголовки.

### Ожидаемые HTTP-заголовки от Gateway

| Заголовок       | Обязательность | Описание |
|-----------------|----------------|----------|
| **`X-Company-Id`** | Обязателен для почти всех роутов | Идентификатор SaaS-клиента (tenant). Используется для изоляции данных. |
| **`X-User-Id`**   | Опционально | Discord ID пользователя. Требуется для операций от лица пользователя. |

### Следствие

Если микросервис получает запрос с заголовком `X-Company-Id` на удаление или изменение сущности, он **доверяет** запросу и выполняет его, не проверяя права пользователя. Проверка прав выполняется на стороне Gateway.

## 2. Multi-tenancy (Строгая изоляция данных)

Приложение обслуживает множество клиентов (SaaS). Данные разных клиентов хранятся в одной базе данных и должны быть **логически изолированы**.

### Правило

Ни один запрос к базе данных (select, update, delete), касающийся бизнес-сущностей, **не должен выполняться без условия** `where: { companyId: '...' }` (или эквивалента в Prisma).

### Реализация

- Заголовок `X-Company-Id` перехватывается на уровне **NestJS Guard или Interceptor**.
- Значение передаётся контекстом (например, через request-scoped сервис или декоратор) во все сервисы и во все Prisma-запросы.
- Все бизнес-сущности в схеме БД должны иметь поле `companyId` (или аналог) и участвовать в условиях выборки и обновления.

## 3. Domain-Driven Design (Модульность / DDD)

Код организуется по **предметным областям (доменам)**, а не по техническому признаку.

### Правило

- Папка со всеми контроллерами, папка со всеми сервисами — **запрещены**.
- Каждый домен инкапсулирует свои контроллеры, сервисы и интерфейсы.

### Структура директорий

- `src/modules/suggestions/` — модуль предложений.
- `src/modules/votes/` — модуль голосования.
- `src/modules/discord/` — модуль интеграции с Discord-ботом.
- `src/common/` — глобальные Guards, Interceptors, фильтры ошибок, утилиты (в т.ч. работа с `X-Company-Id` и контекстом tenant).

## 4. Discord Sharding (Масштабирование бота)

Бот обслуживает тысячи серверов (Guilds). Стандартный запуск через `Client.login()` не выдержит нагрузки и упрётся в лимиты Discord Gateway.

### Правило

Точка входа в приложение (или отдельный скрипт запуска бота) **должна использовать `ShardingManager`** из библиотеки `discord.js`.

### Реализация

- **Основной процесс (Manager)** порождает дочерние процессы — шарды.
- Каждый шард — это **полное NestJS-приложение** (HTTP API + Discord Client): любой инстанс может обработать и API-запрос, и событие Discord своего шарда.
- Файл `main.ts` (или эквивалент точки входа) проектируется с учётом запуска **в режиме дочернего процесса** шарда; инициализация через `ShardingManager` выполняется отдельным скриптом/процессом (например, `shard-runner.ts` или в `main.ts` с ветвлением по переменной окружения/аргументу).
